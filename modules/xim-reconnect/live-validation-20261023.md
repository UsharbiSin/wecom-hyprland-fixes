# 2026-10-23 企业微信输入失灵现场与验收

## 故障证据

环境为 Arch Linux、Hyprland/Xwayland、Wine 11.19-1、
Fcitx5 5.1.23-1、libX11 1.8.13-2、Windows 企业微信 5.0.11.6018。
故障主进程 PID 1383314（UIThread）；Fcitx PID 2978217 于当日 10:42:11 启动。
键盘事件到达企业微信，英文和数字能输入，Rime 激活后仍不出现候选。
主窗口线程没有挂起，焦点和光标正常。只读内存检查显示该线程的 `xim` 为 NULL，其他连接仍有 XIM。
重新公告 XIM_SERVERS 未使主窗口恢复。现场证据与 libX11 多 Display 回调缺陷一致。

## 部署与实测

补丁通过现有启动器的私有 bwrap 文件视图加载，系统原库没有替换。
系统原库 SHA-256：`8d818805efd9e4c08d44981093f99afa2641f3dbefd70770788a570fb7ef8ecf`。
补丁 SHA-256：`ef64aa4947fc8c28a1d8a8dbad007034920a7166ba9b74f20a43c5d641886b6d`。
检查运行中主进程的 `/proc/PID/maps`，确认其映射 libX11 文件；
同时从 `/proc/PID/root/usr/lib/libX11.so.6.4.0` 核对进程文件视图中的补丁哈希。

| 检查 | 结果 |
| --- | --- |
| 重启企业微信后输入 ceshi | 出现“测试”候选 |
| 空格确认候选 | 编辑区出现“测试” |
| 通过 Fcitx Controller Restart 重启输入法 | Fcitx PID 2978217 → 3073343 |
| 重连过程企业微信是否重启 | 主进程始终为 PID 3069554 |
| 重建输入上下文并切回 Rime 后输入 ceshi | 候选恢复，空格确认后正常提交“测试” |
| 切换英文后输入 abc7 | 字母数字正常 |
| 清理 | 测试文字全部删除，恢复 Rime；未发送任何消息，已停止被动跟踪 |

首次重启后过早调用 fcitx5-remote -o，Wine 尚未懒创建新的 IC，随后新 IC 仍默认为英文。
检查确认 XIM 输入上下文已存在且有焦点；在其建立后再激活 Rime，候选和提交均恢复。
该阶段不是重新连接失败，也没有继续修改源码。

## 测试操作事故及恢复

开发中首次 Xvfb 使用自动分配显示号，误选 :0，退出时影响桌面 X0 入口。
现有 Xwayland 及其窗口仍存活，但新连接报 ConnectionRefused，导致第一次企业微信重启未显示窗口。
确认原 Xwayland PID 1295 仍监听 `/tmp/.X11-unix/X0_` 后，恢复 `X0 -> X0_` 入口。
Xlib 新连接、企业微信重新打开及上述输入验收均成功。
已向用户说明此测试操作失误。现有程序未因此被关闭。

最终测试运行器不再使用自动分配；固定 :177，启动前检查同号 socket、备用入口、锁文件、抽象 listener，
并在启动后校验锁 PID 属于自己的子进程；两个 C 测试入口也限制为精确 :177。
这些保护经静态编译和 7 项模拟检查验证，没有为复查保护再启动 Xvfb。

## 范围

本次确认聊天输入及 Fcitx 重启后的重新连接。既有文档、剪贴板等启动器内容保留，未重新做其完整界面回归。
一次成功重连不能覆盖所有输入法或未来版本；系统库哈希变化时本修复会停止加载并提示原因。
